## 一、总体审计意见

**合约：没有已知的高风险问题。前几轮发现的 9 项问题（H-1、H-2、M-1 ~ M-4、L-1、N-1、N-2）都已修复并逐项验证。** 已开局的局不可升级、没有管理员；资金记账守恒；外部市场成交都在同一笔交易里按公式价结算；报价限幅、追价暂停、停运兜底、多数清算底价、随机数重发、哨兵冷静期这些防线现在是一致的。

**本轮新发现 2 个中风险、3 个低风险问题**：

- **G-1（中，合约）**：报价"停运"或"从来没报过"时，两种局的收购价会退回默认曲线，从一年产出的 50% 起涨。市价低时，主板会按两到四倍市价买矿机。修法是报价合约里改 2 行，已验证。
- **G-2（中，机器人）**：主网上"卖一"取自 Firsto 接口里最便宜 3 条挂单的中位数，机器人不在链上核对这些挂单能不能真实成交。有人挂两条假的低价单，就能把报价一步步往下带。合约的限幅和追价暂停把影响限制住了，但上线前机器人必须补上核对。
- 3 个低风险：G-3 报价和其他运营操作共用同一把私钥（并纠正上次的一条建议），G-4 部署检查对 VRF 订阅归属和交易池容量只打印不强制，G-5 前端托管被攻破时的防护。

**结论**
- **合约可以交给正式审计方。** 建议先修 G-1（改动 2 行，打 `v2.0-audit.5`）；如果不想再打一版，就把 G-1 写进 `AUDIT.md` 已知问题，并由运维保证上线时先报价、机器人不长时间停摆。
- **主网上线**还需要：修完 G-2、拿到正式审计报告并公开、完成第五部分的上线前清单。
- 剩余风险集中在信任假设上：运营地址的定价权（被盗时每天最多推动约 4 倍）、手续费 Safe 对新局模板的控制、TapeOut 和 PoD 未开源且可升级、外部市场可升级。这些都已在 `AUDIT.md` 第 5、7 节披露，需要靠监控和应急流程兜住。

## 三、本轮新发现

### G-1（中，合约）：停运或从没报价时，收购按默认曲线进行，可能远高于市价

**位置**：`src/MarketPriceFeed.sol` `buyQuote()`；`TapeBoard.buyPrice()`、`MonthBoard.buyPrice()` 传入的默认曲线（起点 = 一年产出 × 50%，每 6 小时 +5%，60 小时涨到一年产出）。

**问题**：`buyQuote` 在报价"停运"（从没报过价，或 7 天没有有效报价）时返回主板的默认曲线价。合约不知道真实市价，曲线是按"一年产出"定的。按项目自己的行情测算，10 月初矿机约 3 个月回本，也就是市价约为一年产出的 25%。这时曲线起点就是市价的 2 倍，60 小时后是 4 倍；任何人都可以在市场上按真实价格买矿机，再按曲线价卖给主板。

会进入这个状态的情况：
- **上线初期**：机器人还没开始报价，第一块标准局或月局就开局了；
- **机器人停摆 7 天**、手续费 Safe 把运营地址设成 0 后过了 7 天、或者一直追价 7 天（N-2 修复后这三种都会进入停运）。

这时正在收购的局（月局准备期、标准局首轮或补贴开启的新一轮）都会按曲线收购。

**复现测试**（`AuditGlobal.t.sol`，假设市价 = 一年产出的 25%）：
- `test_G1_NeverPostedBoardBuysOnDefaultCurve`：从没报过价，标准局开局后一台 100 算力矿机付了 82.32 BEM，市价只值 41.16 BEM（**2 倍**）；
- `test_G1_AbandonedFeedMonthBoardBuysOnDefaultCurve`：机器人报过一次价后停摆 7 天，新开的月局 60 小时后一台 25 算力矿机付了 41.16 BEM，市价 10.29 BEM（**4 倍**）。

**建议修法**：报过价之后的停运一律暂停收购，只保留"从没报过价"时用默认曲线，并由运维保证上线时先报价：

```diff
     function buyQuote(uint256 cap, uint256 curvePrice, uint256 since) external view returns (uint256 p) {
-        if (abandoned()) return curvePrice;
-        if (!fresh()) return 0;
+        if (updatedAt == 0) return curvePrice; // 从没报过价：默认曲线（上线时机器人先报价）
+        if (!fresh()) return 0;                // 过期、追价、运营地址为 0、停运：一律暂停收购
```

- 卖出一侧不变：停运后月局仍然按成本价可买，参与者能收回本金。
- 暂停收购不会让资金卡住：标准局首轮一台没买到会按保底规则退款，月局准备期没买到会原样退还。
- 已在临时副本验证：全量测试只有 `test/MarketPriceFeed.t.sol` 的 `test_NoOperatorPausesThenFallsBackToCurve` 断言的是旧行为，需要同步改成"停运后收购为 0"，其余全部通过；体积检查通过。
- 上线时：部署完成后、`startGenesis` 之前，机器人先完成第一次报价，写进上线手册。如果想在合约里兜住，也可以让 `BoardFactory.startGenesis` 要求报价合约已经报过价（`BoardFactory` 还有约 14 KB 余量）。

### G-2（中，机器人）：主网报价使用的 Firsto 挂单没有在链上核对

**位置**：`bot/src/market.js` `firstoQuote()`（卖一 = 最便宜 3 条已验证挂单的"日产能价"中位数）、`bot/src/tasks/pricefeed.js` `firstoTargets()`；"保持排序第一"的目标价 `bot/src/markets.js` `floorTarget()` 同理。

**问题**：卖一直接取自 Firsto 公开接口返回的挂单，机器人不核对这些挂单现在能不能真实成交：卖家是否还持有矿机、是否还授权给 Firsto 卖单合约、订单是否已取消或过期。测试网路径反而核对了 `ownerOf`。中位数只看最便宜的 3 条，所以**两条假的低价单就能决定卖一**。而且机器人会把买一限制在卖一以下，买一也会被一起拉低。

**攻击方式**：用两台自己的矿机在 Firsto 挂远低于市价的单，然后撤销授权或把矿机转走，让挂单无法成交。只要 Firsto 接口还显示这两条单，机器人每小时就朝假价格追 5%。合约的防线会让这个过程变慢：每次最多 5%，超过 5% 的距离先进入追价暂停，追到后才恢复交易。所以攻击者需要让假单持续几个小时。之后：
- 标准局市价期按压低的价格卖矿机（最低到采购均价的 60%），攻击者低价买入；
- 月局按"不低于成本"的压低价格卖出，参与者失去溢价；清算计划的底价（买一 × 95%）也会跟着下降；
- "保持排序第一"的目标价同样被带低，但合约把它限制在公式价的 95% 以上、不低于成本，这一项影响很小。

**建议**（机器人改动，不影响合约审计包）：
1. 主网上对参与计算的每一条挂单做链上核对：`ownerOf(tokenId) == maker`、maker 对 Firsto 卖单合约的授权仍然有效、订单没过期；能读到的话，再核对批次 nonce 没有作废。核对不过的跳过；有效挂单少于 3 条就不报价并告警。
2. 要求参与中位数的挂单来自至少 3 个不同卖家，避免一个人用几台矿机控制中位数。
3. 和官方矿机市场、Seaport 的挂单，以及近期真实成交价交叉核对，偏差过大就不报价并告警。
4. 24 小时内目标价累计变动超过一定幅度（例如 15%）时，暂停自动报价，等人工确认。

### G-3（低，合约与运维）：报价和其他运营操作共用同一把私钥

**位置**：`MarketPriceFeed.post / postCatchUp / postFloor` 只认 `BoardFactory.operator()`，和开奖、发放、交接用的是同一个地址。

**问题**：上次报告的运维建议 O-1 是"报价私钥和运营私钥分开"，在当前合约下**做不到**：报价合约只认唯一的运营地址。这样，机器人服务器上的一把热钱包私钥同时握有定价权和全部运营权，H-1 系列风险的入口集中在这一处。这里纠正上次的建议。

**建议**（二选一）：
1. **改合约**：在 `BoardFactory` 加一个由手续费 Safe 设置的 `priceOperator`，报价合约改为只认它。这样可以把报价放到单独的机器或签名服务上，运营地址被盗也动不了价格。两个合约都还有足够的体积余量，主网还没部署，不影响已有局。
2. **不改合约**：接受现状，把机器人服务器当作最高安全等级的资产来保护（专用机器、最小权限、私钥加密存放、出站只连必要的 RPC 和 Firsto）。同时在应急手册里写明：报价异常时由 Safe 立刻更换运营地址（不要设成 0），并把这一点写进 `AUDIT.md` 第 5 节。

### G-4（低，部署脚本）：VRF 订阅归属和交易池容量只打印、不校验

**位置**：`script/DeployMainnet.s.sol` 的预检和 `script/CheckMainnet.s.sol` 的 `_vrf`。

**问题**：两个脚本会打印 VRF 订阅的所有者、两个交易池的观测容量，但不判断是否符合要求。上次的运维建议 O-2（订阅转给 Safe）和 L-4（扩容观测）是否完成，只能靠人工看日志。

**建议**：在 `CheckMainnet` 里改成硬性检查：订阅所有者必须是手续费 Safe；本合约的 VRF 适配器在 consumer 列表里；两个池子的观测容量不低于设定值（按当前出块速度覆盖 2 倍 TWAP 窗口）。任何一项不满足，检查就失败。

### G-5（低 / 信息，dApp）：前端被篡改时的防护

**审阅结果**：dApp 的交易流程做得很好：
- 加入、买持仓、挂买单都按**精确额度**授权，不是无限授权；通行证按编号授权；
- `buyBest` 带最高单价和最高总价，`sellToBid` 以买单当前单价作为最低单价；
- 页面没有矿机买卖入口；
- 打开非官方主板地址时会拦截并提示"不要授权或转账"；
- 每笔交易先模拟再发送。

worker 的鉴权也没有问题：Telegram 回调校验密钥头，绑定用钱包签名加一次性验证码，提醒发送器读名单需要 Bearer 密钥。

**剩余风险**：合约地址打包在前端里，主板合法性校验也读这份地址。如果托管或域名被攻破，攻击者可以换成恶意地址。

**建议**：在白皮书、官方推特、GitHub 等多个渠道公布全部主网合约地址；页面加内容安全策略（CSP）；考虑提供一个 IPFS 镜像；`deployments` 文件的改动走代码评审。
