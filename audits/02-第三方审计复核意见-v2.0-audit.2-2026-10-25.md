## 一、复核结论

**上次的 7 项问题（H-1、H-2、M-1 ~ M-4、L-1）都已正确修复**，改动范围小、思路清楚，没有引入记账、权限或重入方面的新漏洞。文档（`AUDIT.md` 第 3、4、7、26 节和规则决定 6.33）也同步更新了。

**发现 1 个由 H-1 修法带来的新问题（N-1，中风险）**：报价现在每次最多变 5%。行情跳空时，机器人要连续追价好几个小时，这期间报价一直是"有效"的，但偏离真实市价，套利者可以按旧价把矿机卖给正在收购的主板。复现测试里，市场下跌 30% 后的追价过程中，主板多付了 20.58 BEM；如果套利者在第一次追价后就用满 500 BEM 预算，最多可多付约 132 BEM。

修法只需改 `MarketPriceFeed` 和机器人（主网还没部署，不涉及已开局的局）。**建议修完 N-1、打 `v2.0-audit.3` 后再发给正式审计方。** 如果不想再改，也可以原样发 `v2.0-audit.2`，但要把 N-1 写进 `AUDIT.md` 的已知问题，请审计方一并评估。

## 三、新问题 N-1（中）：追价期间报价有效但偏离市价

**位置**：`src/MarketPriceFeed.sol` `post()`、`fresh()`；机器人 `bot/src/tasks/pricefeed.js` 的 `nextPost`（每次朝目标价走 5%）。

**问题**：H-1 修好以后，停报再久，下一次报价也只能比上一次变动 5%。行情跳空（或机器人离线一段时间）后，机器人只能每 50 分钟追 5%：跌 30% 要追 7 次、约 6 小时；第一次报价出错（例如小数位错 100 倍）要追约 94 次、超过 3 天。问题在于，**追价的第一笔报价一上链，报价就重新变成"有效"**，两种局都按这个偏离市场的价格买卖：
- **行情下跌时**：收购价按旧的高价算，套利者在市场上按真实价格买矿机，立刻按报价卖给正在收购的主板；
- **行情上涨时**：标准局按偏低的价格卖矿机（最低到采购均价的 60%），月局按偏低但不低于成本的价格卖，参与者少拿溢价。

机器人如果不报价，报价就一直过期、买卖暂停，永远追不上；只要一报价就会暴露。所以只靠机器人避不开，需要改合约。

**复现测试**（`AuditRecheck.t.sol` 的 `test_N1_CatchUpWindowLetsArbitrageursOverchargeBoard`）：500 BEM 标准局，报价为上限的一半；机器人离线 4 小时期间市场跌了 30%。机器人恢复后分 7 次追价，每次追价后套利者卖一台 30 算力的矿机给主板，主板一共**比真实市价多付 20.58 BEM**。如果套利者在第一次追价后就用满预算，按 95% 对 70% 的价差，最多多付约 132 BEM（约 26%）。

**建议修法**：给报价加"追价模式"。追价期间价格照常按 ±5% 更新，但 `fresh()` 返回假，两种局暂停按报价买卖；追到市价的最后一笔再恢复。被盗的运营私钥并不会因此多出任何权力（每次仍然只能动 5%，最多只能让买卖暂停，而停报本来就能做到）。示意：

```solidity
/// @notice 追价中：价格按 ±5% 更新，但不算有效报价（两种局暂停按报价买卖）
bool public catchingUp;

function post(uint256 newBid, uint256 newAsk, bool live) external {
    // 现有检查不变：运营地址、0 < bid ≤ ask、间隔 ≥ 50 分钟、每次 ±5%
    ...
    bid = newBid;
    ask = newAsk;
    updatedAt = block.timestamp;
    catchingUp = !live;
}

function fresh() public view returns (bool) {
    uint256 t = updatedAt;
    return !catchingUp && t != 0 && block.timestamp < t + maxStaleness && HUB.operator() != address(0);
}
```

配套改动：
1. 机器人：目标价离上一次报价超过 5% 时用 `live = false`；最后一步（目标价在 5% 以内）用 `live = true`。
2. 测试：`AuditRecheck.t.sol` 的 N-1 测试改成断言"追价期间 `buyPrice()` 为 0、月局 `askPrice` 为 0"。
3. 追价期间月局、标准局都是"暂停"而不是"停运"（`updatedAt` 在更新，不会触发按成本价出售），这一点要在测试里覆盖。
4. 第一次上主网报价前，机器人对 Firsto 价格做一次人工核对，避免首笔报价出错。

## 四、剩余风险（不要求改代码，建议在文档和运维中写明）

- **R-1 运营私钥被盗**：每次 ±5%、50 分钟一次，一天仍能把价格推约 4 倍（`AUDIT.md` K10 已写明）。唯一防线是监控告警加手续费 Safe 尽快换运营地址，所以上次报告运维部分的 O-1（报价私钥单独管理）和 O-4（每次报价都告警）要在上线前完成。
- **R-2 月局清算的价格下限依赖运营报的买一**：被盗或合谋的运营地址约 2 天能把买一压到原来的 5% 左右，再配合多数票低价清算。这需要私钥被盗加持续 2 天不被发现，监控到位时风险很低。
- **R-3 VRF 停摆满 7 天后的抢跑**：这时任何人都能调用 `triggerSafeExit` / `triggerSafeSettle`；看到在路上的随机数结果不利时，可以抢先改成保底结局。只在 VRF 连续停摆 7 天的极端情况下出现，VRF 订阅转给 Safe 并监控余额即可。
- **R-4 运营长期缺席时月局无法止损**：报价不新鲜时计划价暂停，停运 7 天后只能按成本价卖。市场低于成本时，多数票也无法低于成本止损，本金会一直锁在矿机里（已知问题 K1 的范围扩大了）。建议在规则文档和 dApp 里写明。
- **R-5 标准局买单在正常终局后基本不可用**：除硅王外都已出局，只能用卖单交易。dApp 下买单时提示即可。
